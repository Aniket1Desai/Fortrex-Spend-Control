## 1. Project Purpose & Scope

### Overview

The **Fortrex Spend Control Tracker (SCT)** is a custom SharePoint Framework (SPFx) web part built with React 17 and backed by Microsoft Dataverse. It is deployed directly onto SharePoint Online modern site pages and connects to the Fortrex Dataverse environment via Azure AD delegated authentication (`user_impersonation`).

### Business Problem

Fortrex operates a **Spend Policy (Draft 2.0)** that mandates:

- **"No PO, No Pay"** — no supplier invoice may be paid unless a valid Purchase Order exists and has been approved through the SCT process.
- All non-PO spend commitments must be authorised *before* any commitment is made to a supplier.
- Requests above defined thresholds must pass through a multi-tier approval chain before a PO can be issued.

Before the SCT, spend requests were managed through email chains and shared spreadsheets, making it impossible to enforce policy, track approval status, or report on committed spend.

### What the SCT Delivers

| Capability | Detail |
|---|---|
| Digitised spend requests | Structured form enforcing all policy rules at point of entry |
| Multi-stage approval routing | Triage → Sourcing → FP&A / CFO → PO Issued → Receiving → Closed |
| Real-time visibility | Dashboard with live Dataverse data and metric stat cards |
| Audit trail | All status changes and approvals recorded in Dataverse |
| Attachment management | Pre-approval evidence and supporting documents via Dataverse Annotations |
| Policy enforcement | Mandatory declarations, conditional field requirements, value-tier attachment rules |

#### `sct_sites_masters` — Site Master

Stores site/location data. When a requester selects a site, cost centre, division, and L1 budget owner are auto-populated (read-only) from this table.

| Logical Name | Notes |
|---|---|
| `sct_sites_masterid` | Primary key (GUID) |
| `sct_site_name` | Display name (PrimaryNameAttribute) |
| `sct_costcenter` | Auto-fills `sct_cost_center` on the request |
| `sct_region` / `sct_division` | Auto-fills division |
| `_sct_budgetownerid_value` | L1 approver lookup |

#### `sct_suppliers` — Approved Supplier List

Pre-approved supplier records. Requesters can select from this list or flag `isNewSupplier = true` to propose a new one (requiring L1+L2+L3 approvals).

#### `sct_roles` — Role Assignments

Used by `ApprovalRoutingService` to dynamically resolve which Dataverse `systemuser` maps to each approval role (Budget Owner, Senior Manager, ELT Leader, FP&A, CFO). Supports delegate substitution and R10 self-approval escalation.

### OData Request Headers

All requests to Dataverse include:

```
OData-MaxVersion : 4.0
OData-Version    : 4.0
Accept           : application/json
Content-Type     : application/json; charset=utf-8
Prefer           : odata.include-annotations="*"
```

The `Prefer` header returns formatted-value annotations (e.g. `sct_request_status@OData.Community.Display.V1.FormattedValue = "Submitted"`) alongside raw integer values.

### Validation Rules (Submit only — not enforced on Save as Draft)

All rules are evaluated in `_validate()` before the Dataverse create call. A red validation summary banner lists all failures above the footer buttons.

#### Mandatory Fields

| Field | Error Message |
|---|---|
| Business Unit | "Business unit is required." |
| Site / Location | "Site / Location is required." |
| Description / Justification | "Description / Justification is required." |
| Purchase Type | "Purchase type is required." |
| Estimated Total Value | "A valid estimated amount greater than zero is required." |
| Date Needed By | "Date needed by is required." |
| Urgency | "Urgency is required." |

#### Mandatory Declarations

Both must be checked before the Submit button is enabled. The Submit button is hard-disabled (`disabled={!declarationNoPriorCommitment || !declarationNoConflictOfInterest}`) — full validation runs only when the button is clicked.

| Declaration | Rule |
|---|---|
| No Prior Commitment | R1 — "No commitment, agreement, or PO has been placed with any supplier prior to SCT approval." |
| No Conflict of Interest | R10 — "I have no personal, financial, or professional conflict of interest with any relevant supplier." |

#### Conditional Requirements

| Condition | Required Field | Error |
|---|---|---|
| `purchaseType` = Repair or Rental | `equipmentAssetTag` | "Asset tag / serial number is required for Repair or Rental." |
| `urgency` = Urgent or Emergency | `urgencyReason` | "Urgency reason is required." |
| `urgency` = Emergency | `emergencyDeclaredBy` | "The person declaring the emergency must be named." |
| `costRechargedToCustomer` = true | `customerName` | "Customer name is required when cost is recharged." |
| `costRechargedToCustomer` = true | `customerAgreementAttached` = true | "Customer agreement or quote must be attached." |
| `isNewSupplier` = true | `newSupplierName` | "Proposed supplier name is required for new supplier requests." |

#### Pre-Approval Evidence Attachment (Approval Matrix Tier)

When `estimatedAmount > 0` or `isNewSupplier = true`, at least one file must be attached as pre-approval evidence:

| Condition | Required Approval Evidence |
|---|---|
| Existing supplier, amt ≤ $2,500 | L1 — Budget Owner written approval |
| Existing supplier, $2,500 < amt ≤ $10,000 | L2 — Senior Manager written approval |
| Existing supplier, amt > $10,000 | L3 — ELT Leader written approval |
| New supplier (any amount) | L1 + L2 + L3 all three written approvals |

If no attachment is present the error reads: *"Written pre-approval evidence from [tier] must be attached before submission."*

### Data Serialisation Fixes

#### `Edm.Date` — Date-Only Fields

Dataverse `DateOnly` columns (`sct_date_needed_by`, `sct_term_start_date`, `sct_term_end_date`) require **strict `YYYY-MM-DD`** format with no time or timezone component. Using `.toISOString()` produces `2024-10-31T00:00:00.000Z` which causes a `400 Bad Request`.

```typescript
function dateOnly(d: Date | null): string | undefined {
  if (!d) return undefined;
  const y  = d.getFullYear();
  const mo = d.getMonth() + 1;
  const da = d.getDate();
  const mm = mo < 10 ? ('0' + mo) : String(mo);  // padStart not in TS lib target
  const dd = da < 10 ? ('0' + da) : String(da);
  return y + '-' + mm + '-' + dd;                 // e.g. "2024-10-31"
}
```

#### `Edm.Boolean` — Boolean Fields

Dataverse boolean columns must receive JavaScript `true` / `false` literals. Sending string `"true"` or integer `1` causes a `400 Bad Request`.

```typescript
payload['sct_is_new_supplier'] = s.isNewSupplier;           // boolean literal
payload['sct_declaration_no_prior_commitment'] = s.declarationNoPriorCommitment;
```

#### OData Lookup Binding (`@odata.bind`)

Lookup fields use the navigation property name with an `@odata.bind` suffix and a server-relative URL:

```typescript
payload['sct_Requester@odata.bind']         = `/systemusers(${requesterGuid})`;
payload['sct_Site@odata.bind']              = `/sct_sites_masters(${selectedSiteId})`;
payload['sct_Suggested_Supplier@odata.bind'] = `/sct_suppliers(${selectedSupplierId})`;
```

#### GUID Validation (Security)

All method parameters that accept a GUID (record IDs, annotation IDs, user IDs) are validated before they are inserted into OData URLs or filter strings:

```typescript
const GUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
function assertGuid(value: string, label: string): void {
  if (!GUID_RE.test(value))
    throw new Error(`Invalid ${label}: expected a GUID, got "${value.slice(0, 40)}"`);
}
```

## 5. Two-Stage Split Approval Workflow

The SCT enforces a **two-phase approval model** aligned to the Fortrex Spend Policy.

### Phase 1 — Pre-Request Written Approval (Before Submission)

The requester must obtain **written pre-approval** from the appropriate level(s) *before* submitting the request. The approval tier is determined by the estimated value and whether the supplier is new:

```
amt ≤ $2,500 AND existing supplier  →  L1 — Budget Owner
$2,500 < amt ≤ $10,000             →  L2 — Senior Manager
amt > $10,000                      →  L3 — ELT Leader
New Supplier (any amount)          →  L1 + L2 + L3 (all three)
```

- The form **shows the required tier(s)** as a guidance banner as soon as the amount is typed.
- The **attachment section** enforces that at least one file is uploaded before submission.
- Written approvals are stored as Dataverse Annotations (Notes) linked to the `sct_request` record.

### Phase 2 — Post-Sourcing Gate (After Sourcing)

Once Procurement has completed sourcing, a second gate is evaluated before the PO can be issued:

```
amt > $10,000  OR  isNewSupplier = true  →  needsGate = true
```

If `needsGate = true`, the request must pass through:

1. **Pending FP&A Review** — Finance (FP&A team) verifies the budget and financial justification.
2. **Pending CFO Approval** — CFO provides final sign-off before the PO authority is granted.

If `needsGate = false` (low-value, existing supplier), Procurement can issue the PO directly after sourcing without FP&A/CFO steps.

This distinction is implemented **client-side** within the "In Review" status — there is no separate Dataverse status value for FP&A vs Sourcing; the gate is determined dynamically from the record's financial fields.

### Rule R10 — Self-Approval Conflict

If the resolved approver for any tier is the **same person as the requester**, `ApprovalRoutingService` automatically escalates to the next level up (e.g. L1 → L2) and flags the record with an `R10 ESCALATED` badge in the Edit panel. This prevents a requester from approving their own spend request.

### Workflow Status Progression

```
Draft
  │  (Submit)
  ▼
Submitted
  │  (SCT Desk picks up)
  ▼
In Review  ◄──────────────── Returned (for information)
  │
  ├─ [needsGate = false] ──► PO Issued
  │
  └─ [needsGate = true]
       │  FP&A Review
       │  CFO Approval
       ▼
     PO Issued
       │
       ▼
     Receiving (goods/services received)
       │
       ▼
     Closed
  
  (At any stage) ──► Rejected
```

## 6. Role-Based Action Panels

The Edit Panel displayed when a user clicks the edit button on a row is **stage-aware**. The fields shown and the footer actions available depend entirely on the current `sct_request_status` of the record.

### Stage Determination

```typescript
const isSubmitted  = statusRaw === DSTATUS.SUBMITTED  || statusLabel === 'Submitted';
const isInReview   = statusRaw === DSTATUS.IN_REVIEW  || statusLabel === 'In Review';
const isPOIssued   = statusRaw === DSTATUS.PO_ISSUED  || statusLabel === 'PO Issued';
const needsGate    = (!isNaN(amt) && amt > 10000) || isNewSupplier;
const isSourceStage = isInReview && !needsGate;   // Procurement / direct PO authority
const isGateStage   = isInReview && needsGate;    // FP&A + CFO required
```

### Panel Stages

#### Triage Stage (`isSubmitted = true`)

Operated by the **SCT Desk / Triage Officer**.

- Displays a read-only Context Strip (10 key fields).
- Shows resolved approvers from `ApprovalRoutingService` with DELEGATE and R10 ESCALATED badges.
- Editable fields: Cost Centre, urgency notes, routing notes.
- Footer actions: **Submit to Sourcing** (moves to In Review) | **Return for Information** (moves to Returned).

#### Sourcing Stage (`isSourceStage = true`)

Operated by **Procurement**.

- Shows read-only context strip.
- Editable fields: Preferred supplier selection, negotiated price, PO date.
- Footer actions: **Issue PO** (moves to PO Issued) | **Return for Information**.

#### FP&A / CFO Gate Stage (`isGateStage = true`)

Operated by **FP&A team** then **CFO**.

- Shows read-only context strip and post-sourcing gate warning banner.
- Displays which approvals are still outstanding.
- Footer actions: **Approve** (advances stage) | **Reject** (moves to Rejected).

#### Receiving Stage (`isPOIssued = true`)

Operated by the **Receiving officer / site contact**.

- Shows PO details and delivery information.
- Footer action: **Confirm Received** (moves to Closed).

#### Default / Read-Only (`Draft`, `Rejected`, `Returned`, `Closed`)

- Panel opens in **view-only mode** — no editable fields.
- Footer shows only **Save Changes** (disabled) to signal no action is available.
- Note: Edit and Delete buttons in the data table are **only enabled for Draft** records; all other statuses render those buttons at 35% opacity and `cursor: not-allowed`.

### Context Strip (Always Visible)

A read-only grey strip at the top of every panel shows 10 key fields regardless of stage:

| Field | Source |
|---|---|
| Reference | `sct_sct_reference` |
| Status | `sct_request_status` (formatted) |
| Requester | `_sct_requester_value` |
| Business Unit | `sct_business_unit` |
| Site | `_sct_site_value` |
| Purchase Type | `sct_purchase_type` |
| Estimated Value | `sct_estimated_total_value` |
| Urgency | `sct_urgency` |
| Date Needed By | `sct_date_needed_by` |
| Submitted Date | `sct_submitted_date` → fallback `createdon` |

## 7. Security & Deployment

### AAD API Permissions

Declared in `config/package-solution.json`:

```json
"webApiPermissionRequests": [
  { "resource": "https://org1bec48f0.crm8.dynamics.com", "scope": "user_impersonation" },
  { "resource": "Microsoft Graph", "scope": "User.Read" }
]
```

Both must be **approved** in **SharePoint Admin Centre → Advanced → API Access** after the `.sppkg` is uploaded.

### Error Boundary

A React `ErrorBoundary` component wraps the entire `AppShell`. If an unhandled render error occurs, an amber recovery card is shown rather than a blank web part. The user can click **"Try again"** to reset the boundary.

### WebPart `onInit` Guard

If the Dataverse `AadHttpClient` fails to initialise (e.g. AAD permission not yet approved), an amber initialisation error card is rendered instead of a blank screen:

```
Fortrex SCT — Initialisation Error
Dataverse service unavailable. Ensure the AAD API permission has been approved
in SharePoint Admin Centre → API Access.
```

### Build & Package

```bash
# Production bundle (TypeScript compile + Webpack)
npx heft build --clean --production

# Package to .sppkg
npx heft package-solution --production
```

**Output:** `sharepoint/solution/ad-dataverse-fortrex.sppkg`

### Deployment Checklist

1. Upload `ad-dataverse-fortrex.sppkg` to the SharePoint App Catalog.
2. Select **"Make this solution available to all sites"** (tenant-wide deployment — `skipFeatureDeployment: true`).
3. In **SharePoint Admin Centre → Advanced → API Access**, approve:
   - `https://org1bec48f0.crm8.dynamics.com` — `user_impersonation`
   - `Microsoft Graph` — `User.Read`
4. In **Power Apps / Dataverse**, ensure the `sct_request` table has **Notes (Annotations)** enabled (`Table Settings → Features → Notes`) to support file attachments.
5. Add the web part to any modern SharePoint page — it appears in the **"Business"** category as **"Fortrex Spend Control"**.
